# 旅遊規劃：依日期新增行程日

研究日期：2026-09-18。狀態：第一批已實作（2026-09-18），第二批（整天改期、自訂月曆、批次新增）仍為提案。

## 建議結論

將「新增一天」改成「新增行程日」，在既有表單最上方提供日期選擇，旁邊顯示對應的 Day N。允許先建立 Day 1、Day 3，之後再補 Day 2；沒有建立的日期不產生空白資料。刪除一天後，其他天的編號與日期保持原樣。

第一階段採用「原生日期欄位＋旅程日期快捷選項」，一次新增一天。這能沿用目前旅程設定的日期操作，也能在快捷選項中清楚呈現哪些日期已建立。多選批次新增與整天改期列為後續功能。

本提案依程式碼與公開介面設計指引整理，未進行使用者訪談或實機易用性測試；以下 UI 尺寸與流程是待驗證的設計決策。

## 現況與問題來源

| 位置 | 目前行為 | 影響 |
| --- | --- | --- |
| `src/app/(app)/trips/[id]/page.tsx` | 新增表單以 `days.length + 1` 顯示下一天 | 一旦有跳號，預覽可能與實際新增結果不一致 |
| `src/components/trips/detail/itinerary/ItineraryDayDialog.tsx` | 日期唯讀，只能填標題、地點與內容 | 使用者不能指定日期 |

| `src/lib/itineraryDayDeletion.ts` | 刪除後把剩餘日重新編為 1、2、3… | 刪掉前面的天會讓後續行程日期前移 |
| `src/models/ItineraryDay.ts` | 儲存 `dayNumber`，沒有獨立日期；`trip + dayNumber` 唯一索引 | 結構可容納不連續天數，不必為空白日期建資料 |
| `src/lib/collectionImport.ts` | 日期＝旅程開始日＋`dayNumber - 1`，以 UTC 日期運算 | Day N 應代表出發後第 N 天，不是第 N 張卡片 |
| `src/actions/itineraryImport.actions.ts` | AI 匯入依指定日期算出 dayNumber，同日已有資料則追加活動 | 已有依日期定位的先例，手動新增應採相同日期算法 |

此外，更新 action 已接受 `day_number`，但目前日編輯表單未提供此欄位。未來不能只在新增 UI 擋重複，還要檢查其他寫入入口的一致性。

## 方案比較

| 方案 | 優點 | 代價／限制 | 決策 |
| --- | --- | --- | --- |
| 原生日期欄位＋日期快捷選項 | 沿用現有操作、手機可用原生選擇器、短旅程一眼可選 | 原生日曆無法自訂逐日「已建立」標記，需靠快捷選項與欄位提示補足 | 第一階段採用 |
| 自訂月曆，標示已建立／可新增 | 跨月、日期分布直覺，未來可延伸多選 | 需引入或建立月曆元件，處理鍵盤、焦點、手機與輔助科技相容性 | 實機驗證有需求後再做 |
| 頂部列出旅程所有日期，空白日期直接新增 | 補空缺容易 | 長旅程橫向捲動負擔大，且會混合「跳到卡片」與「新增」兩種行為 | 首版不更動導覽的既有用途 |
| 自動建立整段旅程所有天 | 不需要逐天建立 | 製造未規劃的空卡片，不符合只新增需要日期的需求 | 不採用 |

原生日期欄位的值可用 `YYYY-MM-DD`，顯示介面則依瀏覽器／語系不同；`min`、`max` 可限制範圍，但仍需伺服器驗證。參考 [MDN 日期輸入說明](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/date)。

## 使用流程與 UI

### 主要情境

旅程為 10/1～10/5，已建立 Day 1。使用者點「新增行程日」，選 10/3，填標題後儲存，頁面顯示 Day 1、Day 3。之後新增 10/2，卡片依日期排序成 Day 1、Day 2、Day 3。

表單示意（日期快捷列超過畫面寬度時換行）：

```text
新增行程日
旅程日期：2026/10/1–10/5

行程日期 *
[ 2026/10/03              日期選擇器 ]
Day 3 · 10 月 3 日

[10/1 已建立] [10/2] [10/3 已選] [10/4] [10/5]
可跳過尚未規劃的日期，之後再補上。

標題 *       [京都散步                  ]
當日地點     [選填                      ]
行程內容     [選填                      ]

                         [取消] [新增行程日]
```

1. 空狀態與既有清單使用相同「新增行程日」入口，維持 admin 才能操作。
2. 預設選取旅程範圍內最早尚未建立的一天。尚無資料時為開始日；Day 1、Day 3 已建立時為 Day 2。使用者可立即改選任何合法日期。
3. 快捷選項只在完整旅程範圍不超過 14 天時全部顯示，使用換行而非藏在橫向捲動中。14 天是首版版面假設，需實機驗證；較長旅程保留日期欄位、已建立日數與「選下一個未建立日期」捷徑，避免渲染大量按鈕。
4. 「已建立」選項不可作為新增目標，使用文字與樣式共同區分。原生日期選擇器可能仍選到已建立日期，此時欄位下顯示「這一天已有行程，請選擇其他日期」，停用新增，提供「查看當日行程」。
5. 有草稿時點「查看當日行程」，需提醒離開會放棄未儲存內容；改選日期則保留標題、地點與內容。單純選日期不寫入資料。
6. 儲存時停用重複送出，顯示「新增中…」。成功後關閉表單，更新清單、捲到新卡片並聚焦卡片標題，提示「已新增 10/3（Day 3）」。導覽定位應共用 sticky header offset 並尊重減少動態效果設定。
7. 失敗時保持表單與草稿，錯誤放在日期欄位或表單內；不只用短暫 toast。日期清單載入失敗時提供重試，不把失敗當成全部日期都可新增。

### 清單與導覽

- 卡片及日期導覽保留真正的 Day N，依 dayNumber 排序；Day 1、Day 3 不改顯示成 Day 1、Day 2。
- 頂部導覽首版仍只包含已建立行程日，避免不存在卡片的 anchor。
- 範圍完整時可補充「已建立 2 / 5 個行程日」；此數字是已建立日期數，不代表活動完成度，也不是旅程只有兩天。
- 空缺不建立佔位卡片。使用者從新增表單補日期，無須先建立空白 Day 2。
- 所有日期都有行程時，入口改為「查看行程日期」，開啟日期列表導向既有卡片，顯示「旅程內的日期皆已建立，可在當日新增活動」。

### 手機與無障礙

- 手機沿用既有 Dialog，日期放在標題前方，內容區可捲動，底部按鈕固定可見；驗證 320px 寬、虛擬鍵盤與安全區不遮住送出按鈕。
- 快捷選項與主要按鈕以至少 44px 點擊高度為設計目標；狀態不只靠顏色，包含「已選」「已建立」文字。
- 日期與天數欄位有明確 label，錯誤透過 `aria-describedby` 關聯，無效時設 `aria-invalid`；更新 Day N 摘要可用 polite live region。
- 日期快捷按鈕提供包含年份、日期、Day N 的可讀名稱，選取狀態使用 `aria-pressed`。開啟表單聚焦日期欄位，取消後回入口。
- 若後續採自訂月曆，需完整支援箭頭鍵移動、月份切換、Escape 關閉及焦點返回，並實測讀屏器；不能只複製範例就視為通過。參考 [WAI-ARIA 日期選擇器範例](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/)。

## 日期與邊界規則

| 情況 | 建議行為 |
| --- | --- |
| 起訖日期皆存在 | 只新增起訖日之間的日期，包含首尾 |
| 只有開始日 | 可選開始日當天或之後；提示「尚未設定結束日期」，不設虛構上限，不顯示完成比例 |
| 沒有開始日，包含只有結束日 | 改顯示「第幾天」正整數欄位，可直接選 Day 3；提示「設定開始日期後即可依日期選擇」，提供旅程設定入口 |
| 未設定開始日的預設天數 | 選最小尚未使用的正整數；送出時明確傳入，不依清單長度推算 |
| 選到重複日期／天數 | 阻擋新增，提供查看原行程；手動新增不自動合併或覆寫 |
| 旅程範圍之外 | 首版不新增；提示先調整旅程日期，不在新增表單自動延長旅程 |
| 舊資料原已超出結束日 | 保留並沿用超出範圍提示，可編輯內容或刪除，不默默截斷 |
| 刪除某天 | 只刪該筆及處理其關聯，不重編其他天；該日期重新成為可新增 |
| 同時有兩位管理員新增同日 | 一位成功，另一位收到日期已建立提示；保留草稿、重新整理可用日期 |
| 表單開啟後旅程起訖變更 | 阻擋使用舊日期基準送出，重新載入日期資訊並保留內容，讓使用者重新確認日期 |
| 跨月、跨年、閏日、不同裝置時區 | 一律以有效日曆日期及 UTC 日差計算，不把本地午夜轉 ISO 後截斷 |

### 旅程改期的取捨

首版沿用現有模型：Day N 相對於旅程開始日。開始日從 10/1 改為 10/2，原 Day 3 就由 10/3 變成 10/4；不是把使用者選取的日期永久固定。

因為新增介面會讓日期更醒目，必須在變更旅程開始日的表單清楚提示「變更出發日期會同步平移所有行程日」，預覽位移天數；移除開始日時提示日期將改為僅顯示 Day N。新增／移除日期的基準變化亦需涵蓋。只改結束日不移動行程，縮短後超出的資料保留並提醒。

若產品希望機票、住宿等行程在整段旅程改期後仍固定原日期，應另案設計獨立 `date` 欄位、改期策略與資料遷移。這不是本次「跳著新增」的必要條件，首版不混用兩種日期真實來源。

## 實作設計

### 資料與 API

維持 `dayNumber` 為資料來源，不增加日期欄位、不補空白天、不需要重新編排舊資料。保留 `trip + dayNumber` 唯一索引。刪除交易的重新編號迴圈必須與新增能力同一批上線。

建議新增輸入採互斥兩種形式：

```ts
// 提案型別，非已存在 API；其餘 title/content/location/activities 沿用。
type DayTarget =
  | {
      date: string; // 嚴格 YYYY-MM-DD，須驗證真實日曆日期
      expected_start_date: string;
      expected_end_date: string | null;
    }
  | {
      day_number: number; // 只供未設定開始日時使用
      expected_start_date: null;
      expected_end_date: string | null;
    };
```

新 UI 必須明確傳目標。為相容仍開著的舊頁面，暫時容許完全未傳目標的舊輸入，沿用 `max(dayNumber) + 1`，但也驗證範圍；回傳實際建立的 DTO。不可把「目標缺漏」「同時傳日期與天數」「格式錯誤」一律當舊輸入吞掉。相容分支仍可能讓舊頁面的預覽不準，因此新版上線後需在既有更新提示流程引導重新載入。

伺服器在既有交易及 parent fence 內：

1. 驗證當下 admin 權限、旅程未刪除，並取得最新起訖。
2. 將 expected 日期與資料庫日期都正規化為 date-only 後比較；不同則回傳提案錯誤碼 `TRIP_DATES_CHANGED`。
3. 有開始日時以選定日期減開始日的 UTC 日差計算：`dayNumber = 日差 + 1`；不信任前端預覽數值。無開始日時驗證 day_number 為安全正整數。
4. 驗證範圍、檢查同日是否存在，建立資料並保留既有附件檢查與照片重綁流程。
5. 捕捉唯一索引衝突並轉成 `DAY_ALREADY_EXISTS`；超界回 `DATE_OUTSIDE_TRIP`，缺開始日回 `TRIP_START_DATE_REQUIRED`，非法日期回 `VALIDATION_ERROR`。這些錯誤碼需加入實際 ActionResult 與翻譯支援。

新增、AI 匯入共用日曆日期／dayNumber 轉換及範圍判斷；保留兩者不同的同日策略：手動新增阻擋，AI 匯入仍依原流程追加。既有 `updateItineraryDay(day_number)` 也需驗證範圍與唯一性，避免繞過規則；內容更新不應因此阻擋舊的超界行程（已實作：只有真的換天才檢查，並沿用同一組錯誤碼）。

| 區域 | 預計工作 |
| --- | --- |
| 行程頁與 `ItineraryDayDialog` | 新增模式可選日期／天數，移除 `days.length + 1`，草稿與錯誤狀態、成功定位；編輯模式日期維持唯讀 |

| `itineraryDayCreation.ts` | 交易內依目標建立，日期與衝突驗證 |
| `itineraryDayDeletion.ts` | 移除重編；保留費用解除關聯、照片清理／重綁、附件退役 |
| 旅程日期編輯 UI | 開始日變更的行程位移預覽與提示 |

| 測試 | 修正「刪除必須連號」舊預期，新增日期與交易情境 |

需回歸檢查費用關聯選擇、統計、地圖、相簿、公開分享、匯出、AI 匯入及活動帶入航班／住宿。以穩定 day ID 維持關聯；所有顯示 Day N 的地方不可使用陣列 index 代替。旅程總天數、已建立行程日數、已有活動天數是不同指標，不全面把所有 `length` 換成最大 dayNumber。

新增／刪除後沿用 itinerary、photos 快取更新，另檢查費用與統計等實際 query key：刪除會改變費用關聯，需要讓已載入的相關畫面取得最新結果。

## 交付順序與驗收

第一批完整交付包含日期／天數選擇、預設空缺日、交易驗證、不重編刪除、開始日改期提示、錯誤與無障礙處理。先完成資料規則及交易，再接 UI；新增能力與刪除語意不可分開部署。沒有行為上線前，不把提案寫成 FEATURES 現況。

第二批再依回饋評估整天移至其他日期（需 revision、照片重綁及既有活動連結策略）、自訂月曆、批次選取不連續日期。批次新增需另定標題產生方式、同日衝突與部分成功行為。

| 驗收情境 | 預期 |
| --- | --- |
| 先建 Day 1，再選 Day 3 | 只有兩筆資料，顯示 Day 1、Day 3，日期正確 |
| 第一筆直接選 Day 3 | 不自動建立 Day 1、Day 2 |
| 再補 Day 2 | 插入正確日期位置，原有 ID、活動與關聯不變 |
| 刪除 Day 2，或刪除 Day 1 | 其餘 dayNumber、日期、revision 不因重編而改變 |
| 相同日期重送／兩人同時新增 | 只有一筆，不覆寫；失敗端可保留內容改選日期 |
| 起訖邊界、非法日期、跨年、閏日、DST | 合法日期對應正確 Day N；無效與超界被 server 擋下 |
| 無開始日、只有開始日、只有結束日 | 使用上述替代流程，之後設定開始日能正確推算日期 |
| 開表單後他人改旅程日期 | 不誤建到其他天，明確提示並更新日期資訊 |
| AI 先匯入 Day 3，再手動建立或刪除 | 跳號維持；同日手動不覆寫，AI 既有追加策略不變 |
| 照片、費用及統計 | 空缺日不錯配；刪除只清除該日關聯，快取同步 |
| 手機與鍵盤 | 320px 不橫向溢出；鍵盤可完成、錯誤可讀、成功定位不被 sticky header 遮住 |
| 長旅程及所有日期已建立 | 無巨量快捷按鈕；有明確查看既有行程路徑 |

實作時以日期 helper 單元測試、Dialog 互動測試及既有 itinerary concurrency 整合測試覆蓋核心規則；再實機檢查 iOS Safari、Android Chrome 與桌面鍵盤／讀屏操作。第一批已補上日期 helper 單元測試與 Dialog 互動測試，並更新 itinerary concurrency 整合測試（含更新入口換天的範圍／唯一性情境；需 `MONGODB_ITINERARY_TEST_URI` replica set 才會執行，本機尚未實跑）；實機瀏覽器與讀屏驗收尚未執行。
