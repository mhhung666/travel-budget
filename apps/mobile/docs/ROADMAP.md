### 3. E1：建立與加入旅行

**建立旅行**：旅行列表及空狀態提供「建立旅行」「加入旅行」。建立頁包含名稱（trim 後 1–100 字）、說明（選填，最多 2,000 字）、開始／結束日期（各可空；提供時須是真實 date-only，兩者皆有時開始不得晚於結束）。不新增目的地欄位；沿用後端空值，避免把純文字假裝成現有地理位置物件。上述上限為 E 新規格，共用服務及 Web 新建表單同步驗證，歷史長內容仍可讀。

使用者按「建立」才凍結表單及 UUID，先落盤再送出。建立旅行、唯一邀請碼、建立者 admin 與 receipt 同一交易完成；新碼以密碼學安全亂數產生，維持既有 6–10 碼相容性，碰撞由資料庫唯一約束與有限次重試處理。成功重新讀列表並進入新旅行摘要；本人花費／餘額為零。回應遺失時以原 UUID 找回同一旅行，不按名稱猜測是否成功、不建立第二份。

**加入旅行**：輸入接受 6–10 碼英數邀請碼（trim／轉小寫）或目前 API 環境對應 Web origin 的 `/join/{code}` 連結。連結只解析，不抓取任意 URL；拒絕不符 origin／路徑、ObjectId、虛擬身分認領連結及其他分享連結。手機首版用貼上入口；Universal Links／App Links 留 F，不以 Expo Go deep link 當正式能力。

按鈕明示「加入旅行」，此點擊就是加入確認，不先提供非成員帳務預覽。後端在交易內重新核對有效碼、刪除狀態與成員狀態；新加入者為 member。已是成員回成功並導向原旅行，不重複新增成員、通知或動態。無效／過期／已重設的碼統一顯示無法加入；不回傳私人內容。舊請求在加入成功後又遭移除時，重播／查詢不可自動重新加入；重新加入須由使用者使用仍有效的碼發起新確認。

**邀請入口**：旅行摘要提供「邀請成員」，僅目前成員明確開啟時取得邀請碼與由後端設定產生的 Web 邀請 URL；可複製或使用系統分享。一般列表／摘要 DTO 不附加分享碼；登出、換帳號與撤權清除畫面及記憶體資料，不保存碼到一般查詢快照或分析 log。提示持有碼者可加入，且沿用現有 Web 分享邊界；E 不建立新的唯讀碼或審核加入機制。重設邀請碼仍在 Web。

加入成功後重讀 landing／expense-options，成功授權讀取後才建立本機快照；不直接把加入回應當成離線授權證據。

### 4. E2：註冊與重設密碼

已實作共用服務、匿名 HTTP、手機畫面與故障回歸；寄碼 429 誤鎖驗碼的 P2 已分開操作期限修正，程式審查及獨立複驗通過；兩平台基本操作依約待 E1–E4 全部完成後統一驗收，見 [本機驗收](LOCAL_ACCEPTANCE.md#e2-帳號入口驗收交接)。現行 API／限流與環境限制見 [後端契約](BACKEND_CONTRACT.md#e2-註冊與-email-驗證碼重設)。以下保留產品規則；匿名 HTTP 不使用 E1 receipt，也不保存密碼。

**註冊**：登入頁新增「建立帳號」「忘記密碼」。欄位為帳號、顯示名稱、Email、密碼、確認密碼；確認密碼只供 UI，不送 API。帳號 trim 後 3–200 字、顯示名稱 trim 後 1–100 字、Email trim 並沿用既有格式與不分大小寫唯一規則。沿用既有至少六字元密碼政策，不自行 trim 密碼；新設密碼加上 bcrypt 的 72 UTF-8 bytes 上限，兩端提示一致，既有登入輸入相容性不因本片改動。

Mobile 註冊成功回最小 user DTO，回登入頁並帶入帳號，由使用者登入；不自動建立手機 session，避免「帳號已建立、憑證保存失敗」被顯示成註冊失敗。Web 可維持成功後建立 cookie，由 adapter 負責。重複帳號／Email 統一 `ACCOUNT_CONFLICT`，不暴露是哪個欄位已存在。資料庫唯一索引處理同時註冊；新帳號不會自動認領虛擬成員、不額外新增 Email 啟用流程。

註冊逾時／5xx 顯示「結果尚未確認，可先嘗試登入」，不自動重送、不落盤密碼，也不以公開查詢 API 確認帳號是否存在。使用者可明確重新註冊或回登入／忘記密碼。

**忘記密碼**：輸入 Email → 通用受理訊息 → Email／六位數碼／新密碼／確認密碼 → 重設成功 → 回帳號登入。六位碼用字串保存前導零；15 分鐘有效、最多五次錯誤嘗試，重新寄送成功產生新碼後舊碼失效。Email 不存在／存在均回相同受理內容；受理不等於保證信件已送達。錯碼／過期／次數用盡提供可行的重新寄送入口，不洩漏帳號資料。

密碼更新與驗證碼消耗須在同一交易內，錯誤嘗試須原子累加並條件檢查；同一碼併發最多成功一次，重新寄碼與舊碼驗證的競態不能讓舊碼覆寫新密碼。密碼更新成功後，現有 mobile session 的密碼 fingerprint 檢查使舊憑證失效；不假稱現有 Web cookie 也會因此全部失效（Web cookie 機制目前不同）。本機草稿與 C／D／E 待確認紀錄保留，重新登入原帳號後恢復。

**限流**：重設寄碼按正規化 Email 每 60 秒最多一次、每小時五次；存在與不存在 Email 共用相同計數。驗碼除每碼五次外，按 Email 每 15 分鐘十次；註冊／寄碼另按後端可信來源位址每小時二十次，避免只靠 UI 倒數。這些是首版設定值，可配置且須由兩個 adapter 共用；不可直接信任用戶自填的 forwarded header，實作時按既有部署入口固定解析，無可信位址時保留 Email／帳號限制並明列環境限制。計數只存 keyed hash，不記明文密碼／驗證碼；429 回 Retry-After。匿名限流與已登入帳務共用等待分開。

密碼／驗證碼只保留當次畫面記憶體，離開或成功清除；不進 SQLite、Query、log 或正式截圖。Email 寄送沿用現有後端服務；測試用隔離寄信 adapter／測試收件匣，不能以讀正式信件或正式 log 作驗收。寄送逾時不得由 App 不斷自動寄碼；重設提交逾時可嘗試新密碼登入，不能斷言一定沒改成功。

### 5. E3：編輯與刪除已入帳支出

**入口與載入**：明細頁提供「編輯」「刪除」，兩者都先在線上取得最新編輯上下文。沿用現有協作模型，admin／member 都可操作，不只限建立者或付款人。編輯表單與 D 新增草稿分開；不會覆蓋該旅行的新增草稿。後端回支出、最新選項、不透明 `revision`、可編輯能力及受限原因，手機不以 amount／splits 猜測原始分攤模式。

**首版編輯模式**：

| 模式         | 可改欄位                         | 保留規則                                                                                                         |
| ------------ | -------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 基本資料     | 說明（1–200 字）、分類、真實日期 | 外幣、匯率、付款人、原始金額及分攤完全保留；未知歷史分類不默默寫回 other                                         |
| TWD 重新均分 | 上述欄位＋金額、付款人、分攤成員 | 只限原 TWD／匯率 1 且可解析的有效成員；使用者明確選「重新均分」，由既有後端 preview 產生分攤，確認新舊差異後提交 |

預設基本資料模式，因此非均分舊帳不會只因打開並保存就變均分。TWD 非均分支出可在明確選擇重新均分後轉換；外幣、失效成員、超出手機金額範圍或無法安全映射的歷史資料，只開放後端判定可用的基本資料欄位，其餘提示到 Web 處理。付款人可以不在分攤名單；金額 0.01–1,000,000,000.00、最多兩位小數、成員 1–100 位，沿用現有預覽與尾差規則。

只傳使用者實際修改的白名單欄位；未支援的附件、標籤、行程關聯、建立者、建立時間及既有 receipt 不變。基本資料模式不得要求重送舊金額／分攤，也不得把 DTO 的歷史補值或 null 成員當作原始資料寫回。沒有變更不送 PATCH。重新均分時必須送完整金額／付款人／後端分攤；禁止落入現有 Web「只改金額、未送 splits 就自動均分」的隱含分支。改輸入、成員或斷線皆取消新預覽，重新確認後才送。

**衝突**：`expected_revision` 與寫入在 `withTripWrite` 同一交易核對。建議 revision 使用後端對原始可變業務欄位的穩定 HMAC，綁定 tripId／expenseId，包含付款人、原幣／金額／匯率、分攤、說明／分類／日期、附件／標籤／行程關聯，以及當前成員 ID 順序；不用 `createdAt` 當版本，也不依賴目前沒有的 updatedAt。所有 Web／虛擬身分轉換／行程解除關聯造成的有效內容變更，以及成員順序變更都應改變 token，背景 outbox 狀態不影響 token；內容完全還原時 token 可相同，此為狀態前條件而非變更歷史。簽章域與登入憑證分開，token 不洩漏欄位內容。

他人先修改時回 `409 RESOURCE_CHANGED`，保留本人尚未送出的輸入，顯示最新內容與差異；只能重新載入後手動套用並確認，不能靜默覆蓋或自動合併分攤。已被刪除顯示不可編輯；同旅行不存在單筆支出不等於整個旅行被撤權。重播先查原 receipt 再判前條件，自己成功後版本變動不會把成功重播判成衝突。

**刪除**：確認頁顯示說明、日期、付款人、TWD 金額，警示會影響結算並刪除相關評論／附件關聯，無還原功能；取消零寫入。使用 UUID 與 expected_revision 刪除；使用者看確認頁後內容被他人修改就先報衝突，要求重新確認。伺服器同交易寫 receipt、刪 expense／comments 並安排既有 blob retirement；外部檔案清理失敗不把已刪除改報成未刪。原建立 receipt 不刪除，舊 C／D 重播不能讓支出復活。

成功後離開已刪除明細，或重新載入已更新明細；重讀支出第一頁、結算、landing 及旅行列表摘要。不先樂觀改餘額；已成功但重讀失敗顯示「操作完成，資料更新失敗」與只讀重試。

### 6. E4：登記與撤銷還款

**入口**：結算的建議轉帳列提供「登記已付款」，另有「手動登記」。前者預填付款人、收款人與建議金額；兩者都進可調整表單，最後顯示「誰付給誰、多少 TWD、備註」讓使用者確認。畫面明示 App 只記錄已在外部完成的還款，不執行轉帳；建議不是已付款紀錄。

欄位為付款人／收款人（不同的當前旅行成員，以 id 辨識同名）、金額（0.01–1,000,000,000.00、最多兩位小數）、備註（trim 後最多 200 字）。沿用 Web 信任模型：任何成員可代其他成員登記，包含虛擬成員；支援部分還款、無建議的手動還款及高於建議金額的實際付款，不把建議額當硬上限。偏離建議須清楚顯示確認，不能標成「已全部結清」；是否歸零由後端重算。

開表單及確認前取得新的 payment context：最小成員選項、目前 settlement 及 `settlement_revision`。revision 綁定旅行，對成員 ID、支出 ID／計算輸入與 payment ID／金額／方向生成不透明狀態 token，在同一 trip write 交易內重算／比較，避免兩人同時照舊建議各記一筆。所有影響這些結算輸入的變更（包含 D 前景佇列寫入、Web 支出或還款）都會觸發衝突；回 `409 SETTLEMENT_CHANGED` 時保留輸入，重讀並要求再次確認，不能自動替換金額後送出。不同 UUID 仍可在新狀態下經明確確認登記同額付款，不按金額誤判重複。

**撤銷**：還款歷史提供「撤銷這筆登記」，任何成員可操作；確認方向、金額與備註後刪除該 payment，並重算結算。若真有新一筆反向付款，應另建新紀錄，不能用撤銷冒充退款。撤銷使用自己的 UUID 及 payment revision（至少包含付款／收款原始 ID、金額、備註），避免虛擬成員認領等變更後沿用舊確認。成功時原 payment-create receipt 仍保留，重播不得恢復被撤銷的付款。

登記或撤銷成功後刷新結算、旅行列表與 landing；不在 Mobile 另算帳務。通知／動態保留既有業務語意，同一操作重播不再觸發；E 不增加催款或刪除通知功能。

### 7. HTTP 契約與後續提案

所有路徑以下省略 `/api/v1`；輸入延續 snake_case、回應 camelCase。沿用嚴格 JSON、8 KiB、no-store 及 `{ data }`／`{ error: { code }, requestId }` envelope；欄位未知回 400。契約實作時只定義於 packages/contracts，不把下表複製成另一套 runtime schema。

| 交付  | 路徑                                              | 輸入與成功回應摘要                                                                                    |
| ----- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| E1    | `POST /trips`                                     | UUID、name、description、start_date／end_date → `{ tripId }`，200 含重播；後續讀現有 landing          |
| E1    | `POST /trips/join`                                | UUID、invite_code → `{ tripId, alreadyMember }`；只以有效碼解析                                       |
| E1    | `GET /trips/:id/invitation`                       | 成員 Bearer → `{ code, url }`；不放進一般 Trip DTO                                                    |
| E1 起 | `GET /mutation-requests/:uuid`                    | 原帳號 Bearer → `not_found`／`committed`（operation、resourceId、最小結果）／`rejected`（終局拒絕碼） |
| E2    | `POST /auth/register`                             | username、display_name、email、password → 最小 user，200；不回 token                                  |
| E2    | `POST /auth/password-reset/request`               | email、locale → `{ accepted: true }`；不表示實際送達                                                  |
| E2    | `POST /auth/password-reset/confirm`               | email、code、new_password → `{ reset: true }`；無自動登入                                             |
| E3    | `GET /trips/:id/expenses/:expenseId/edit-context` | expense、options、revision、capabilities／限制原因                                                    |
| E3    | `PATCH /trips/:id/expenses/:expenseId`            | UUID、expected_revision、mode、changes → `{ expenseId, revision }`                                    |
| E3    | `DELETE /trips/:id/expenses/:expenseId`           | JSON UUID、expected_revision → `{ expenseId, deleted: true }`                                         |
| E4    | `GET /trips/:id/payment-context`                  | members、settlement、settlementRevision、各 payment 的 revision                                       |
| E4    | `POST /trips/:id/payments`                        | UUID、expected_settlement_revision、from_id、to_id、amount、note → `{ paymentId }`                    |
| E4    | `DELETE /trips/:id/payments/:paymentId`           | JSON UUID、expected_revision → `{ paymentId, deleted: true }`                                         |

UUID 欄位為 `client_request_id`；E UUID 統一小寫正規化。PATCH 的 mode 為 `basic` 或 `equal`，changes 必須非空且按模式使用嚴格 schema，不能夾帶其他欄位。一般成員路徑只接受 ObjectId 並重新授權；404 統一涵蓋非成員、旅行不存在及他旅行資源，不能 fallback public API。邀請碼只在加入／明確取邀請這兩個入口流動；匿名 auth 路徑不接受成員資料操作。

`edit-context`／`payment-context` 在一致的資料快照內產生內容與 token，不能先算版本、再讀另一時間的資料。沿用既有 expense preview；能力由後端判斷。新增服務不可強迫舊 App 升級；舊 DTO、C receipt 與現有新增 body 維持相容，E 的 context 是獨立端點，舊 receipt 不需要新增欄位。

### 8. 共用寫入、恢復與 C／D 整合

E1／E3／E4 的每次確認以一個 UUID 表示，Mobile 在同一 SQLite DB 新增獨立 E 操作表（不塞進 expense_queue）：環境、帳號、操作種類、旅行／資源 id、UUID、前條件及凍結 body、狀態、最早可重試時間。主鍵按環境／帳號／UUID；必要的邀請碼只留在這份待確認 payload，結案即清除，不記 log。沒有 token／密碼。schema 升級保留舊草稿、pending、queue 與帳號限速，交易失敗不送 HTTP。

狀態為「可編輯 → 已確認並落盤 → 送出中 → 已完成／確定拒絕／結果不明」。結果不明期間不能修改 body、改 UUID 或捨棄；可離開畫面，在旅行列表提供「待確認操作」入口，建立／加入尚無 tripId 也找得到。App 啟動／回前景／重新連線只自動查詢 E 結果，**不自動重送 E 寫入**；原內容重試由使用者明確操作。不要把不可捨棄的已送出操作與可捨棄 D queued 混用。

伺服器新增 E mutation receipt：以操作者＋UUID 唯一索引，指紋包含操作種類、目標、前條件及標準化 body。同 key 不同操作／內容回 `409 IDEMPOTENCY_CONFLICT`；同 key 同內容回原結果。新 E receipt 不變更既有 ExpenseCreateRequest 格式；不設短期 TTL，也不隨 expense／payment 刪除消失。trip 刪除後保留最小結果但對已無授權者不回傳私人資源。索引與 schema 遷移須可在隔離環境重跑，遠端 migration 另行安排。

寫入授權／前條件、業務異動、receipt 在同一交易；重播先重新授權，再查 receipt，最後才檢查新寫入前條件。加入的首次交易尚無成員資格，需用有效碼及 trip fence 專門處理；不能套用要求既有 member 的 withTripWrite。重播既有加入 receipt 時要求目前仍是成員，不能再次執行加入。建立旅行則使用帳號層 UUID receipt 與 Trip 同一交易，不能因尚無 tripId 而略過去重。

| 結果                          | 客戶端規則                                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------------------- |
| 200／committed                | 本機結案，再讀最新資源；receipt 的歷史結果不能直接覆蓋後來已編輯／刪除的資源                        |
| rejected                      | 伺服器終局 receipt 證明原操作未提交；解除 pending，保留非敏感輸入供重新確認，以新 UUID 表達新的意圖 |
| 409 前條件衝突                | 儲存終局拒絕結果再回覆；重新讀取、人工確認；不可和 UUID 內容衝突混為一談                            |
| 409 UUID 衝突                 | 保留原紀錄、只查原結果；不自動換 UUID 或以另一種操作覆蓋                                            |
| 401／403／404／refresh 失敗   | 停止送出、隱藏無權私人內容、保留原帳號紀錄；不可把「查不到／沒權限」當未寫入                        |
| 429                           | 保存原始絕對期限、等待到期；不能因本機攔截再延長、刪紀錄也不能清期限                                |
| 5xx／逾時／斷線／不可解析回應 | 結果不明，查 receipt 或明確以原 UUID／body 重試；不顯示確定失敗                                     |
| not_found                     | 目前沒終局 receipt，不代表原請求不在執行；不准另開新 UUID 替代                                      |

輸入在開始寫入前被 API 400／413／415 拒絕，只能證明這次嘗試未寫；先前已有不確定嘗試時仍不能清除 pending。若目前旅行授權有效、原操作尚未提交但目標已被他人刪除，保存 `RESOURCE_GONE` 終局拒絕供查詢結案；不可僅憑一般 404 推論此狀態。可重試的交易中止／429 不保存為終局拒絕。可安全終局化的業務拒絕與成功都要在 UUID 競爭下只有一個結果；先查 receipt 並以唯一鍵／交易解決競爭，不能事後獨立寫一份拒絕覆蓋成功。

E 的已登入寫入與結果查詢共用現有帳號／環境限速；舊欄位／表可先保持名稱，經共用 adapter 擴充，避免搬表破壞 C／D。匿名註冊／寄碼不共用這個 scope。收到 429 取 `max(原期限, 新期限)`，本機攔截沿用原值；SQLite 等待、序列等待及 refresh 後每次 fetch 前同步再查期限和登入／撤權世代。

同一旅行有 C pending、D prepared 或 E 結果不明時，不啟動另一筆 E 帳務寫入；E 帳務 pending 也阻擋該旅行 D 的下一筆交接。使用共用序列及持久化檢查，不能只靠畫面 disabled。D 尚未準備的 queued 不必清空，也不永久鎖住 E；在序列中取得執行權後讀新預覽／context，已有 pending 優先結案，其查詢及原 UUID 恢復不被自己的鎖擋住。A 的衝突只擋 A；只有帳號限速擋所有旅行。E1 未知 tripId 的建立／加入先按操作範圍防雙擊，取得 tripId 後刷新既有旅行狀態。

副作用在提交後執行、依操作去重；沿用既有耐久清理／通知設施，不在會被 DB 重試的交易 callback 寄信或呼叫外部服務。不承諾外部郵件 exactly-once；至少保證重播不再次排程，同一操作不重複活動／通知紀錄，副作用失敗不讓已提交的寫入變成失敗。

### 9. 驗收與完成條件

每片需要單元測試、隔離真 MongoDB replica set／實際 HTTP；兩平台基本 UI 操作依上述決定於全部 E 功能完成後統一驗收。E1／E3／E4 另驗真 SQLite 重開，E2 驗原生登入及安全儲存流程；以 UUID／receipt／expense／payment／會員陣列及副作用數核對，不只看成功提示。

| 交付 | 必須通過的案例                                                                                                                                                                                                              |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1   | 無日期／單側日期／跨年／閏日、空白名稱、倒置日期；建立丟回應重啟只一旅行；舊 6 碼與現行碼、有效連結／外站連結／ObjectId；併發加入只一 member；原已加入／重設碼／刪旅行／加入後撤權；邀請頁換帳號不殘留                      |
| E2   | Web／Mobile 互登入；大小寫及空白正規化唯一衝突；UTF-8 密碼邊界；不存在 Email 的回應及限流一致；前導零碼、過期、第五次錯誤後阻擋；兩個正確驗碼併發只成功一次、重寄競態；提交丟回應可登入核對；舊 Mobile token 失效但草稿保留 |
| E3   | metadata 編輯保留外幣／非均分／附件／標籤／行程；明確重新均分才改份額、0.01 三人尾差；Web 同時改帳／刪帳、虛擬身分轉換及行程解除造成前條件衝突；刪除清評論／blob retirement、建立 receipt 保留；刪後舊 C 重播不復活         |
| E4   | 同名／虛擬成員、部分／超額／無建議還款、0 或負數／第三位小數拒絕；兩人用同一建議併發只一個前條件成功；重試同 UUID 只一 payment；撤銷後結算還原、create receipt 重播不復活；Web 互讀一致                                     |
| 共用 | 持久化失敗零 HTTP；送前／交易前後當機、5xx／丟回應、清理失敗、重啟、A→B→A／跨環境、撤權晚到回應、429 真實期限及 SQLite／refresh 競態；C／D／E 同旅行序列與跨旅行繼續；終局成功／拒絕競爭不矛盾                              |

每個新表單在 iOS／Android 驗證四語、深淺色、預設／最大字級、鍵盤捲動與動作鍵；付款方向、同名成員、危險確認、busy／disabled／錯誤焦點需有無障礙標籤與程式測試。完整 VoiceOver／TalkBack／真機範圍仍依暫緩決定列 F，但 E 新增畫面納入同一份待驗清單，不能沿用 D 通過結果。

跨 workspace 的每片交付依根規範執行 frozen install、contracts:generate／check、check、test:run、build、export:check，另做 Mobile Expo 相容性檢查及受影響 Web 操作回歸。部署順序為向下相容的後端／必要索引先行、App 後行；不以已合併代表已部署。

E 完成定義：四片上述能力與必要故障案例通過、Web 既有流程無退步、C／D 資料與重啟行為相容、功能／契約／驗收文件同步，剩餘人工項目明列且無未處理的帳務／權限程式 P2。這是進入 F 的開發完成條件，不是可直接對外發布的宣告。
