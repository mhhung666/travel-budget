# 任務交辦 prompt 範本

> 讀者：主對話模型。用法：複製對應範本，填空 `【】`，用 Agent 工具發出並照表指定 `model`。
> 每份範本已內建交辦三要素（目標與動機／驗收條件／回報格式）與回報合約（見 [DISPATCH.md](DISPATCH.md) §3–4）。
> 通用鐵則：回報長度上限必填；「不確定寫未確認，不准編造」必留；長產物存檔傳路徑。

## 1. 搜尋（agent: Explore，model: haiku；錯一次→sonnet）

```
你在 /Users/mhhung/Development/travel-budget（Next.js 16 + MongoDB 旅行記帳 app）。

目標：找出【要找的東西，例：所有呼叫 getReceiptUrl 的地方】。
動機：【為什麼找，例：要改它的簽章，需要知道影響面】。
範圍：【目錄或全 repo；搜索廣度 medium / very thorough】。

驗收條件：
- 每個結果附 檔案:行號 與一行說明（它在做什麼）。
- 明確說「找完了」或「以下範圍沒掃到：…」，不要默默漏。

回報格式（≤40 行）：條列 `路徑:行號 — 說明`；最後一行寫結論（共幾處／沒找到）。
不確定的寫「未確認」，不准編造路徑。
```

## 2. 實作（agent: general-purpose，model: sonnet）

```
你在 /Users/mhhung/Development/travel-budget。先讀 CLAUDE.md（硬規則）與【相關的 docs/claude/*.md 或 docs/ARCHITECTURE.md 段落】。

目標：【做什麼，含具體行為描述】。
動機：【使用者要解決的問題——邊角情況照這個動機取捨】。
已知入口：【檔案:行號，主對話已定位好的起點】。
不要做：【明確排除項，例：不要改 public API、不要動 schema】。

驗收條件（逐條自驗後才算完成）：
- 【功能驗收點 1、2…】
- JUDGMENT.md §2 的「【對應型態】」checklist 逐條通過（用 grep/指令驗證，貼出驗證指令與結果）。
- `pnpm test:run` 綠、`npx tsc --noEmit` 乾淨、`pnpm lint` 過。

回報格式（≤50 行）：
## 改了什麼（每檔一行：路徑 — 動了什麼）
## 驗收核對（逐條 ✓/✗ + 驗證指令輸出摘要）
## 未解決/需人工確認（沒有就寫「無」）
失敗也要回報：卡在哪、錯誤全文存到 scratchpad 哪個檔。
```

## 3. 重構（agent: 先 Plan(model: opus) 出計畫 → 再 general-purpose(model: sonnet) 執行）

```
【Plan 階段】
你在 /Users/mhhung/Development/travel-budget。目標：規劃【重構什麼】的執行計畫，不要動手改。
動機：【現況痛點】。約束：對外行為不變；遵守 CLAUDE.md 硬規則；分成可獨立驗證的小步。
驗收條件：計畫列出步驟順序、每步涉及檔案、每步的驗證方式、風險點與回退法。
回報格式（≤60 行）：編號步驟清單。

【執行階段——每步一發，或小計畫一發】
目標：執行以下重構計畫的第【N】步：【貼上該步驟】。
不要做：計畫以外的「順手改善」；行為變更；跳過測試。
驗收條件：該步驟的驗證方式通過 + `pnpm test:run` 綠（重構期間測試必須始終綠，紅了先停）。
回報格式（≤30 行）：改動檔案清單 + 測試結果 + 下一步是否可續。
```

## 4. 研究（agent: Explore 或 general-purpose，model: sonnet；查 Claude Code 本身→claude-code-guide）

```
目標：回答【問題】，供【接下來的什麼決策】使用。
動機：【答案會影響什麼】。
資料來源優先序：【官方文件 URL / repo 內程式碼 / docs/】。版本、參數、API 名稱必須查證到來源，不准憑訓練記憶。

驗收條件：
- 每個結論附來源（URL 或 檔案:行號）。
- 區分「已確認」與「未確認/查無」，未確認不可混進結論。

回報格式（≤60 行）：先一段直接回答，再列證據；最後列「查不到的部分」。
超過 60 行的原始資料存到 scratchpad，回傳路徑。
```

## 5. 審查／驗證（agent: general-purpose，model: 驗檔案 haiku / 驗程式 sonnet / 對抗審查 opus。必須 fresh spawn，不能用寫作者本人）

```
你是獨立審查者，沒有參與實作，對「已完成」的宣稱保持懷疑。

目標：驗證【變更/檔案】是否真的滿足驗收條件。
動機：實作者不能自驗（DISPATCH.md §6）。

驗收條件清單（逐條核對，回 ✓/✗ + 證據）：
1. 【條件一——寫成可機械核對的形式，例：grep X 應出現在 4 個 catalog】
2. 【條件二…】
3. `pnpm test:run` 實跑結果（貼摘要，不貼全文）。

另外主動找碴（各至少想一個，找不到就寫「無」）：
- 邊角情況：【例：空清單、離線、非成員存取】
- 違反 CLAUDE.md 硬規則之處
- 宣稱做了但檔案裡不存在的東西（read-back：親自打開檔案核對，不信轉述）

回報格式（≤40 行）：逐條 ✓/✗ 表 + 找碴發現（附 檔案:行號）+ 最終判定：通過／退回（退回要給可執行的修正指示）。
```

## 委派後，主對話要做的三件事

1. 收到回報先掃「驗收核對」段：有 ✗ 或缺漏 → 依 [DISPATCH.md](DISPATCH.md) §5 升降級，不急著自己下場修。
2. 把「未解決/需人工確認」轉給使用者或開新委派，不要吞掉。
3. 踩到雷（agent 誤解 prompt、範本缺欄位）→ 照 [MAINTENANCE.md](MAINTENANCE.md) 把教訓寫回 LESSONS.md。
