# 給未來 session 的信

> 寫於 2026-07-04，Fable 5 唯一一次 session 的收尾。讀者：使用者本人，以及之後接手的每一個模型。

## 一、三件你沒問、但我認為最重要的事

**1. 這套制度的生死取決於「入口」，不是內容。**
Claude Code 每個 session 常載的只有 CLAUDE.md；docs/claude/* 全靠連結被點開。弱模型最常見的失敗不是讀不懂規則，是**根本沒去讀**。所以：(a) CLAUDE.md 的「Working protocol」段落是整套制度唯一的入口，任何人想在 CLAUDE.md 塞新內容時，優先犧牲別的，不能犧牲它；(b) 交辦重要任務時，使用者只要多打一句「照 DISPATCH.md 辦」，命中率會高非常多——這是整套制度裡 CP 值最高的一句話。

**2. 把三個安全契約從「文件約束」升級成「測試約束」，比任何 prompt 工程都值錢。**
此 repo 最怕的失效模式是弱模型「好心修壞」安全邊界，而目前這三個契約只有文件在守：
- `/api/public/*` 永不回收據附件（`attachments: false`）；
- 公開地圖 API 永不露旅程名稱/id/完整日期（只有年份）；
- `/api/public/*` 只收 hash_code、不收 ObjectId。
建議：花一次功夫寫成整合測試（對 route handler 的回應斷言「不含這些欄位」）。機器擋規則比文件擋可靠一百倍，這是我建議的下一個工程任務（已符合 IMPROVEMENTS.md 的收錄標準）。

**3. 制度補得了執行，補不了品味——別讓它給你假信心。**
拆解、checklist、fresh-context 驗證能把 Sonnet 的**執行品質**拉到接近高階模型；但 UX 文案取捨、API 設計品味、「這個功能該不該做」這類模糊題，弱模型照著 rubric 也答不好。遇到這類題的正確動作在 JUDGMENT.md §3：升級到 opus 拿第二意見，或直接問使用者。制度的誠實條款：**它讓便宜模型不犯蠢，不讓便宜模型變聰明。**

## 二、這套制度最可能的退化方式與預防

| 退化方式 | 訊號 | 預防（已內建於制度） |
|---|---|---|
| CLAUDE.md 膨脹回長文 | 每次「順手加一條」 | 150 行硬上限；加新規則屬「先問使用者」（MAINTENANCE §2） |
| 文件與程式碼漂移 | 引用的路徑 404、regex 對不上 | 「引用前先驗證」（LESSONS 第一條）；季度查核（MAINTENANCE §4） |
| LESSONS.md 變垃圾場 | >30 條沒人整併 | 門檻 + 「重複兩次就升格為正式規則」（MAINTENANCE §3–4） |
| 範本 cargo-cult | 照抄 PROMPTS.md 但驗收條件留空 | 「三要素缺一不發」（DISPATCH §3）；主對話收報告先掃驗收段 |
| 驗證退化成自驗 | 實作 agent 自稱「我驗過了」就放行 | 「寫的人不能驗」（DISPATCH §6）；審查範本強制 read-back |
| 制度檔沒人讀 | 行為與 DISPATCH/JUDGMENT 明顯不符 | 見上文第一點：守住入口 + 使用者一句「照 DISPATCH.md 辦」 |

## 三、誠實清單：這次哪些產出信心最低、為什麼

1. **DISPATCH.md 的任務→模型對照表與升降級門檻**（信心最低）：模型別名與參數是查證過的，但「haiku 錯一次升級」「兩輪重試上限」這些**門檻值是我的判斷，不是此 repo 的實測數據**。用幾週後應該根據實際錯誤率調整——調整屬使用者決定（MAINTENANCE §2）。
2. **effort 欄位未實測**：官方文件確認 `.claude/agents/*.md` frontmatter 有 `effort: low|medium|high|xhigh|max`，但本專案還沒有任何 agent 定義檔，我沒實跑驗證過。建檔時先開一個小的試。
3. **CLAUDE.md 的 @import 語法**：本次派 agent 查官方文件**查無佐證**，所以制度完全不依賴它（全用普通連結按需讀）。若日後官方文件確認支援，可考慮把 DISPATCH 的 §3–§5 摘要設為常載——屆時注意常載總量要克制（CLAUDE.md 本身已有 150 行硬上限）。
4. **「被導向 Opus 4.8 的請求是否消耗 Fable 窗口額度」：未確認**。我在此環境查不到，也不編造。建議到 claude.ai 的 usage 儀表板實測比對。
5. **DIAGNOSIS.md 的「前三名」排序**：是我對這個 harness 失效模式的判斷（證據：本次審計就抓到文件自相矛盾），但不是量測結果。若實際踩雷分布不同，照 MAINTENANCE §3 用 LESSONS.md 累積證據後修它。
