## 1. 結論先行

目前產品的 UI 已經從「功能堆疊」進入有系統的產品介面階段，整體成熟度約 **3.5 / 5**。既有的 App Shell、行動端底部導覽、旅行內四個主分頁、語意化色彩 token、Responsive Form Sheet、空狀態、Skeleton、離線提示，都值得保留。

下一輪不建議再做一次大規模換皮，而應集中改善以下三件事：

1. **更快完成第一個成功任務**：註冊後應一路引導到「建立旅行 → 新增第一筆支出 → 邀請同行者」，目前建立旅行成功後只回到列表，空狀態也沒有內嵌 CTA。
2. **讓記帳在任何位置都容易開始，而且不容易記錯**：高頻任務不應先找旅行、再切到支出；日期、幣別換算、分帳人數與每人金額也應在送出前明確可見。
3. **減少功能成長造成的導覽與頁首負擔**：桌機有 6 個頂層入口，行動端又把其中 3 個收進「我的」；旅行內同時存在頁首、主分頁、子分頁、摘要條與全域底部導覽，資訊正確但密度偏高。

建議先完成本文件剩餘的 P0，不需要先改品牌色或重做所有頁面。Phase 1A／1B 已建立金額、日期與操作可及性基線，Phase 2A 已接通首次成功路徑，Phase 2B 已提供全域快速記帳，Phase 3 也已收斂資訊架構、旅行首頁與邀請銜接；Phase 4 的自動化與量測程式基線已完成，下一步是部署後累積指標並執行 5–7 人任務測試，再依一致證據決定是否調整導覽。

## 2. 產品核心使用情境

UI 的優先順序應由以下 Jobs-to-be-Done 決定：

| 使用情境 | 使用者真正想完成的事 | 介面應優先保證 |
| --- | --- | --- |
| 第一次使用 | 快速建立一趟旅行並知道下一步 | 低認知負擔、明確下一步、快速得到價值 |
| 旅途中記帳 | 幾秒內記下剛發生的消費 | 隨時可開始、預設值可靠、單手操作 |
| 多人分帳 | 確認誰付款、誰分攤、各自多少 | 金額與參與者清楚、送出前可核對 |
| 旅後結算 | 知道「我該付誰／誰該付我」並完成還款 | 以我為中心、可追蹤已付與未付 |
| 規劃與回顧 | 查行程、票券、相片、統計與成就 | 容易找到，但不干擾高頻記帳 |
| 網路不穩 | 先記錄，恢復連線後確認已同步 | 狀態可見、失敗可恢復、不重複送出 |

產品定位雖已擴展到行程、相簿、地圖、成就與會籍，主要價值仍是「旅行中的多人記帳與分帳」。只要入口或資訊層級有衝突，應優先保護記帳與結算。

## 4. 現有設計中應保留的部分

### 4.1 兩層空間模型是正確方向

全域 App Shell 管理旅行、地圖、統計與個人功能；進入單一旅行後，再由 [TripSpaceShell](../src/components/trips/space/TripSpaceShell.tsx) 管理行程、支出、相簿、結算。這比把所有功能放在同一層導覽更符合使用者心智模型。

### 4.2 高頻支出表單已經大幅簡化

[ExpenseFormSheet](../src/components/trips/detail/expense-form/ExpenseFormSheet.tsx) 將流程排序為「金額 → 描述 → 分類」，其餘欄位收進進階區，並在行動端使用 100dvh 全螢幕 Sheet、固定送出鍵。這是目前體驗最成熟的流程，不應退回長表單。

### 4.3 結算已從系統觀點改為使用者觀點

[SettlementSummary](../src/components/settlement/SettlementSummary.tsx) 優先回答「你應收／應付多少」，而不是先展示全團總支出；相關轉帳也排在前面。這符合使用者在結算頁的第一個問題。

### 4.4 視覺基礎已足夠支撐後續優化

[globals.css](../src/app/globals.css) 已有淺色／深色共用的 primary、success、warning、info、destructive token；元件層也禁止散裝 Tailwind 調色盤色。下一步應補齊互動與版型規則，不需要再換品牌色。

### 4.5 行動端與 PWA 細節有被納入

目前已有 safe-area、底部導覽、全域快速記帳、離線 banner、待同步支出標記、Service Worker 更新提示與 PWA quick-add shortcut。這些都是旅行場景真正會遇到的問題。

## 5. P0：下一輪應優先完成

P0 的定義是「在新增更多功能前先處理」。每項都直接影響任務完成率、金額正確性或使用信任。

### P0-1 建立一條完整的首次成功路徑

**現況**

- 登入／註冊成功後進入 `/trips`。
- 沒有旅行時，[EmptyTripsState](../src/components/trips/EmptyTripsState.tsx) 只有說明文字，沒有內嵌「建立旅行」與「加入旅行」CTA。
- 建立旅行表單一次展示名稱、描述、出發地、目的地、日期與好友。
- 建立成功後關閉表單、重新載入列表，沒有直接進入新旅行。
- 行程與支出空狀態雖提示「點擊新增」，但空狀態本身沒有 action。

**問題**

使用者完成註冊後仍要自己理解產品架構。新手最需要的是「下一步」，不是完整功能列表。FAB 對既有使用者有效，但不應是新手唯一的建立入口。

**建議流程**

```text
註冊完成
  → 建立第一趟旅行（只要求旅行名稱；目的地與日期可略過）
  → 直接進入旅行
  → 顯示 3 步輕量 checklist
      1. 新增第一筆支出
      2. 邀請同行者
      3. 設定常用幣別（可略過）
  → 完成第一筆支出後收起 checklist
```

不要做多頁強制教學。以頁內 checklist、空狀態 CTA 與一次性提示引導即可。

**驗收條件**

- 空旅行列表同時提供「建立旅行」主 CTA、「輸入邀請碼」次 CTA。
- 建立旅行第一屏只要求名稱；其餘內容標示為可選或收進「加入更多資訊」。
- 建立成功後直接導向新旅行，且清楚顯示下一個建議動作。
- 行程、支出、清單、相簿等關鍵空狀態都能直接執行主要動作。
- 可記錄 activation funnel：完成註冊、建立旅行、新增第一筆支出、邀請第一位成員。

### P0-2 提供全域快速記帳入口

**現況**

- 行動端新增支出 FAB 只在旅行的支出分頁出現。
- PWA manifest 有 `/quick-add` 捷徑，但一般網頁內沒有同等入口。
- 使用者在地圖、統計或「我的」頁，要先進旅行，再切到支出，才能新增。

**問題**

「剛付完錢立刻記一筆」是最高頻、最有時效性的任務，不應依賴使用者目前位於哪一頁。PWA shortcut 只能服務已安裝且知道捷徑的使用者。

**建議**

- 行動端底部導覽改為：`旅行｜地圖｜＋記一筆｜我的`，將低頻「個人統計」移到「我的」或旅行洞察入口。
- 桌機頂列提供清楚的「記一筆」主按鈕。
- 若只有一趟進行中旅行，直接開啟該旅行的新增支出表單。
- 若有多趟可能的旅行，先顯示最近／進行中的旅行 picker；記住上次選擇。
- 沒有旅行時，「記一筆」應轉為建立旅行流程，而不是無回應。

是否取代現有「統計」底部項目，應以實際點擊率驗證；但全域快速記帳的可見性不應低於統計。

**驗收條件**

- 從任一主要頁面開始，兩次操作內可進入金額輸入。
- 有一趟進行中旅行時，一次操作即可開始輸入。
- 返回原頁後保留原本捲動位置與篩選狀態。
- 快速入口與 PWA shortcut 共用相同的旅行選擇規則。

### P0-3 在送出前清楚呈現「這筆帳會怎麼記」

> 狀態：✅ Phase 1A 核心範圍已完成（`0f249b6`）。尚待補強金額輸入對科學記號等瀏覽器邊界格式的限制。

**評估時現況**

- 新增支出預設今天、目前使用者付款、所有成員均分。
- 進階區收合時只顯示「日期 · 付款人 · 分帳模式」。
- 沒有直接顯示分帳人數、每人金額、換算後 TWD 金額。
- 多個結算與分帳畫面用裸 `$` 表示 TWD，在多幣別產品中容易被理解為 USD。
- 今天的預設值使用 `new Date().toISOString()` 取日期；在 UTC+ 時區的凌晨，存在預設成前一天的風險。

**問題**

預設值讓輸入更快，但被藏起來的預設也可能造成「很快地記錯」。金額產品最重要的是可預測與可核對。

**建議**

在主要欄位下方放一個可點擊的「記帳摘要」，例如：

```text
你付款 · 今天 · 4 人均分
每人 TWD 285 · 共 TWD 1,140
```

外幣時改為：

```text
JPY 6,000 ≈ TWD 1,260
你付款 · 4 人均分 · 每人約 TWD 315
```

點摘要直接展開並定位到付款人／日期／分帳區。日期應以使用者本地時區建立，不應從 UTC ISO 字串截取；所有 TWD 顯示統一用 `NT$` 或 `TWD`，不要用無上下文的 `$`。

**驗收條件**

- [x] 送出前不展開進階區，也能看到付款人、日期、參與人數、分帳方式與每人金額。
- [x] 外幣支出可看到原幣、匯率狀態與換算基準幣金額；無有效匯率時阻止送出，不再靜默使用 `1.0`。
- [x] 核心支出、分帳與結算金額透過同一 formatter 呈現；TWD 不再顯示為裸 `$`。
- [x] 本地日期 helper 已涵蓋 UTC+8 凌晨與 UTC- 時區單元測試，並套用至支出、統計、飛行、住宿與會籍補登。
- [ ] 金額欄位除拒絕 0、負數與非有限值外，再明確限制非預期科學記號等瀏覽器邊界輸入。

### P0-4 建立可及性與觸控基線

> 狀態：✅ Phase 1B code baseline 已完成（`6bc3b3f`）；完整 axe 與登入後任務式鍵盤測試保留在 Phase 4。

**評估時現況**

- 旅行行程、清單、成員、留言、還款紀錄等多處 icon-only 操作只有 28–36px。
- 部分按鈕只有 `title`，沒有本地化的 accessible name。
- 金額 Hero input 移除了可見 focus ring。
- ResponsiveFormSheet 的描述使用 `hidden`，而不是只在視覺上隱藏的 `sr-only`。
- 部分 aria-label、DialogDescription 與錯誤訊息仍硬編碼英文或中文。
- 尚無元件互動／鍵盤／axe 類型的自動化測試。

**問題**

旅行中常是單手、走動、強光或不穩定網路環境。小按鈕不只是 WCAG 問題，也會直接增加誤觸刪除與操作失敗。

**建議基線**

- 所有主要觸控目標至少 44 × 44px；視覺 icon 可維持 16px。
- icon-only 按鈕必須有四語系 accessible name，不只靠 `title`。
- 鍵盤操作時所有互動元件都有清楚的 focus 樣式。
- Dialog／Sheet description 使用 `sr-only`，不要從 accessibility tree 隱藏。
- 支援 `prefers-reduced-motion`，非必要的滑入與 hover 位移可停用。
- 導入 axe 或同等檢查，至少覆蓋登入、旅行列表、新增支出與結算。

**驗收條件**

- [x] 共用 Button、Input、Select、Toggle、Tabs、Menu、Dialog、Sheet 與 Toast 已有可見鍵盤 focus；公開相簿 lightbox 支援 Escape、方向鍵、Tab trap 與關閉後 focus return。
- [ ] 登入後的旅行列表、新增支出與結算仍需以真實資料完成一次完整鍵盤任務測試。
- [x] 360px 公開入口實際渲染無水平溢出或主要動作遮蔽；登入後頁面與瀏覽器 200% zoom 留待 Phase 4 裝置矩陣驗證。
- [ ] 關鍵頁面無 serious／critical 自動化可及性問題。
- [x] 刪除、編輯、複製、關閉、上一張／下一張等 icon-only 控制已補四語名稱，並有可重跑的 AST 靜態測試防止新增未命名按鈕。
- [x] 支出金額欄位已有可見 focus；表單 description 保留在 accessibility tree。
- [x] 支出表單的付款人、匯率更新與進階分帳控制已補四語 accessible name 與 44px 觸控目標。

## 6. P1：完成 P0 後的結構改善

### P1-1 收斂全域導覽，讓桌機與行動端心智模型一致

目前 [AppShell](../src/components/layout/AppShell.tsx) 桌機頂列有旅行、地圖、統計、成就、會籍、年度回顧 6 個入口；[BottomTabBar](../src/components/layout/BottomTabBar.tsx) 行動端只有旅行、地圖、統計、我的，成就、會籍與年度回顧收進「我的」。

建議將全域資訊架構收斂為：

| 層級 | 建議入口 | 內容 |
| --- | --- | --- |
| 主要 | 旅行 | 旅行列表與旅行空間 |
| 主要 | 地圖 | 個人旅行地圖 |
| 主要動作 | 記一筆 | 情境式快速記帳 |
| 主要 | 我的 | 帳號、好友、通知、外觀 |
| 我的／洞察 | 統計、成就、會籍、年度回顧 | 個人長期資料與低頻回顧 |

桌機可以保留「統計」為直接入口，但成就、會籍、回顧較適合放進「我的旅行資料」下拉或次級頁面。不要讓桌機與行動端看起來像兩套產品。

### P1-2 減少旅行空間的 sticky 高度

旅行內目前可能同時顯示：

- 旅行名稱與返回／更多
- 4 個主分頁
- 子分頁
- 總支出／預算摘要
- 全域底部導覽

在小螢幕上會明顯壓縮內容。建議：

- 捲動後將旅行名稱列縮為 compact mode。
- 總支出摘要在行程／相簿可收合，支出／結算保留完整資訊。
- 主分頁與子分頁避免重複命名：`行程 > 每日行程／隨手記／清單`、`結算 > 結算方案／群組統計`。
- 超過一層的低頻設定維持在「更多」，不要再增加新主分頁。

### P1-3 讓旅行落點依階段回答不同問題

目前旅行落點先顯示旅行資訊卡，再顯示每日行程。對新旅行合理，但對旅途中每天打開 App 的使用者，靜態旅行資訊會重複占據首屏。

建議依狀態調整：

- **行前**：距離出發日、未完成待辦、下一個行程。
- **旅途中**：今天是 Day N、今日活動、快速記帳、今日花費。
- **旅後**：待結算金額、未完成還款、相簿與回顧。
- 旅行資訊改為 compact cover；需要時再展開或到設定編輯。

這比永久顯示相同資訊卡更有情境感，也能讓「行程」成為真正的旅行首頁。

### P1-4 優化邀請與加入流程

目前加入對話框要求輸入旅行 ID／Hash Code，描述仍有硬編碼英文；旅行卡則直接突出顯示代碼。

建議：

- 輸入框可接受代碼或完整邀請 URL，貼上後自動解析。
- 行動端優先使用原生分享面板，並提供 QR code 供面對面加入。
- 邀請頁先清楚展示旅行名稱、日期、目的地與邀請者，再要求登入。
- 旅行代碼屬於管理／分享資訊，不必在每張旅行卡上與日期、目的地同等突出；可移入更多選單。
- 加入成功後直接進入該旅行，不只刷新列表。

### P1-5 強化離線同步的可見性與復原

現有離線 banner 與單筆「待同步」是好基礎，但當多筆資料排隊或同步失敗時，使用者缺少集中入口。

建議增加簡單的同步狀態：

```text
離線 · 3 筆待同步
正在同步…
2 筆完成 · 1 筆需要處理
```

失敗項目應能重試、編輯或刪除本地草稿。重新連線並全部成功後，顯示一次「已同步」回饋即可，不要持續打擾。

## 7. P2：視覺、內容與細節精修

### 7.1 補齊版型 token，而不只色彩 token

目前色彩系統完整，但頁面仍混用 `rounded-lg`、`rounded-xl`、`rounded-2xl`、多種陰影與卡片內再包卡片。可定義：

- Surface：page、section、card、floating。
- Radius：control、card、modal 三級。
- Elevation：flat、raised、overlay 三級。
- Spacing：頁面區塊、卡片內距、表單間距。

結算頁的卡片中再包成員卡片可改為分隔列，減少視覺重量。

### 7.2 統一產品詞彙

建議建立 content glossary：

| 概念 | 建議統一用詞 |
| --- | --- |
| Trip | 旅行 |
| Itinerary | 行程 |
| Expense | 支出 |
| Settlement | 結算 |
| Payment record | 還款紀錄 |
| Member | 成員 |
| Virtual member | 虛擬成員 |

避免同一層混用「旅行詳情／旅行空間／旅程」、「ID／Hash Code／邀請代碼」。四語系應用相同 glossary 與格式規則。

### 7.3 統一日期與金額格式

- 所有日期 formatter 明確使用 UI locale，不依瀏覽器預設 locale。
- 日期區間使用同一格式與分隔符。
- 基準幣與原幣同時存在時，先顯示原幣，再顯示約當 TWD。
- 不用裸 `$`；使用 `TWD 1,234`、`NT$1,234`、`USD 40.00`。
- 四捨五入時顯示「約」，結算實際入帳值則顯示精確規則。

### 7.4 空狀態應包含情境動作

通用 [EmptyState](../src/components/common/EmptyState.tsx) 已支援 `action`，但多個呼叫端只給文字。建議空狀態至少回答：

1. 這裡為什麼是空的？
2. 使用者現在可以做什麼？
3. 完成後會得到什麼？

「搜尋無結果」則應直接提供清除篩選，而不是只寫提示。

### 7.5 登入首頁補足價值與信任

目前首頁以登入卡和趣味圖片為主，適合回訪者，但新使用者不容易理解：

- 是否支援多人？
- 是否支援外幣與離線？
- 資料是否公開？
- 加入別人的旅行是否一定要註冊？

可在不拉長頁面的前提下，補一個實際產品畫面或三點價值說明，並區分「建立自己的旅行」與「使用邀請連結加入」。趣味品牌圖可保留，但不應承擔主要產品說明。

## 8. 關鍵畫面建議

### 8.1 行動端新增支出

建議資訊層級：

```text
┌────────────────────┐
│ TWD      1,140     │
└────────────────────┘

[ 午餐、交通費、飯店住宿… ]

[🍜 餐飲] [🚆 交通] [🏨 住宿] [更多]

每人 TWD 285

加入收據、標籤、行程日、匯率…             >

┌────────────────────┐
│      新增支出       │
└────────────────────┘
```

分類不一定要一次展示全部；可顯示常用前三個加「更多」，並根據最近使用排序。若保留完整分類網格，也應確保不會把摘要與送出鍵推離主要視線。

### 8.2 旅行首頁

```text
大阪旅行                         ⋯
Day 3 · 7 月 27 日

下一個行程
14:30  大阪城

[記一筆] [看今天行程] [開啟票券]

今天已花 TWD 3,420
預算剩餘 TWD 18,600

待處理
2 個清單項目 · 1 筆待同步
```

旅行資訊、分享代碼與管理功能放進次級入口。旅行首頁應回答「現在要做什麼」，而不是再次列出靜態旅行資料。

### 8.3 結算

第一屏只回答：

```text
你應付 TWD 1,280

付給 Amy       TWD 980      [登記已付]
付給 Ken       TWD 300      [登記已付]

查看全體結算方案
查看每人成本明細
```

與自己無關的交易、每人付款統計與匯率切換可放到第二層。這能延續目前「以我為中心」的方向。

## 9. 設計系統補強

建議在現有 Shadcn + token 基礎上，補一份小而明確的 UI 規格，而不是導入新的大型 design system。

### 9.1 元件規則

| 元件 | 規則 |
| --- | --- |
| Primary button | 每個畫面／區塊最多一個最強主動作 |
| Icon button | 44px 觸控區、16–20px icon、必須有 accessible name |
| Destructive action | 不與一般操作並排搶主視覺；執行前確認，完成後可恢復者優先提供 undo |
| Form field | label、help、error 各有固定位置，不以 placeholder 取代 label |
| Empty state | icon、原因、下一步 CTA；無結果狀態附清除條件 |
| Toast | 用於完成通知；需要使用者處理的錯誤留在畫面內 |
| Skeleton | 形狀應貼近最終內容，避免載入後大幅位移 |
| Money | 全站使用單一 formatter，原幣／基準幣層級一致 |

### 9.2 狀態規則

每個可寫入功能至少設計以下狀態：

- 初始／空
- 載入中
- 成功
- 欄位錯誤
- 系統錯誤
- 離線排隊
- 同步中
- 同步失敗
- 權限不足／唯讀

目前多數功能已有其中數種，但尚未形成一致契約。

## 10. 量測與驗證

沒有行為資料時，不應只憑設計偏好決定導覽。建議先加入不含敏感金額內容的事件量測。

### 10.1 核心指標

| 目標 | 指標 |
| --- | --- |
| 新手得到價值 | 註冊後 10 分鐘內建立旅行率、第一筆支出完成率 |
| 快速記帳 | 開啟表單到成功送出的中位時間、欄位修改次數 |
| 降低錯帳 | 新增後 2 分鐘內編輯／刪除率、日期與分帳欄位修改率 |
| 導覽可理解 | 各主要功能進入路徑、返回／繞路比例 |
| 邀請成功 | 分享邀請到加入完成的轉換率 |
| 離線可信 | 排隊 mutation 成功同步率、失敗後成功復原率 |
| 可及性 | 鍵盤關鍵流程通過率、自動化 serious/critical issue 數 |

不要記錄支出描述、成員名稱、旅行名稱、精確金額或邀請碼。

### 10.2 建議的可用性測試任務

找 5–7 位會與朋友出國、曾使用 Splitwise／試算表／聊天群記帳的人，測試：

1. 建立一趟三人日本旅行並邀請同行者。
2. 記錄 JPY 6,000 晚餐，由自己付款、三人均分。
3. 修改成其中一人不參與。
4. 在離線狀態新增一筆交通費，恢復連線後確認結果。
5. 找出自己應付誰、登記部分還款。
6. 從邀請連結加入別人的旅行。

觀察完成率、時間、回頭次數、誤觸與口頭疑問；不要在測試中提示介面位置。

- 真實裝置上的視覺與鍵盤測試。
