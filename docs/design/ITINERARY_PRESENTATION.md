# 行程共用版面與跨日活動

更新：2026-11-06。狀態：規劃，尚未實作跨日資料與顯示；Web 日卡 UI-W 已完成，App UI-M 待做並併入本計畫。這份文件是兩端版面與跨日規則的唯一規格；既有多選／恢復規則見 [活動多選刪除](ITINERARY_BATCH_DELETE.md)。

## 目標與範圍

- Web／App 使用相同資訊順序、操作分區、名稱與跨日語意；Web 窄版和 App 必須用同一組資料逐項對照，不能只統一文案。
- 活動仍歸屬開始的每日行程；完整內容只存一筆，結束日可顯示導回原活動的提示。日期不明時不假裝已知。
- 先共用後端與 Web，再 App，最後兩端延續提示與聯合驗收。跨日多選 BD3、整天改期、多日住宿管理、時區換算／飛行時長、自動建立空白日不在本輪。

## 兩端統一版面

層級固定為「旅行 → 每日行程 → 活動」，旅行分頁仍叫「行程」。桌面與手機只調整換行和彈層形式，資訊順序不變。

視覺以現有 Web 日卡為基準：相同的主次字級層級、語意色、分隔線、留白節奏與按鈕強弱；使用各端既有 theme tokens，不硬搬 CSS 到 React Native。一般間距採 8／12／16／24 的對應節奏，操作區至少 44px／pt；文字自然增高，不用固定列高或縮字解決溢出。iPad／桌面使用限寬內容，沒有額外資訊時不硬排成雙欄。

「本日設定」含「編輯本日資訊」「刪除這一天」；日表單用「本日標題／地點／備註」，新增日用「新增一天」。刪除整天仍顯示真實日期、名稱、活動數及既有關聯影響，不暗示縮短旅行或重編天數。Web 既有票券／照片／成就能力保留；App 未實作的能力不放假按鈕。

## 跨日顯示與編輯

以 1/12 22:25 出發、1/13 00:20 抵達為固定對照案例：

```text
Day 1 · 1/12  出發                         本日設定 ▾
本日備註……
──────────────────────────────────────────────────
當日活動 · 1 項                 選取活動  ＋新增活動
22:25         ✈ CX469 TPE–HKG                     ⋯
翌日 00:20      1/12 出發 → 1/13 抵達
```

```text
Day 2 · 1/13  東京                         本日設定 ▾
↳ 接續前一天
  00:20 抵達 · CX469 TPE–HKG       查看原活動 →
──────────────────────────────────────────────────
當日活動 · 4 項                 選取活動  ＋新增活動
00:30         住宿活動……                           ⋯
```

時間語意：

- 當日結束：保留兩行起／迄時間，不額外貼「跨日」徽章；翌日使用「翌日 00:20」，不單獨用 `+1` 或顏色傳達。
- 超過一日：有日期時顯示明確日期，未設旅行日期時用「第 N 天」；顯示完整起訖摘要，無障礙名稱也包含日期關係。
- 航班／交通摘要用「出發 → 抵達」，其他活動用「開始 → 結束」。未設定開始或結束時間顯示「時間未定」，不補 00:00、不計算時長；僅知道日期也能表達。
- 舊資料未確認結束日：保留既有時間，若結束時間小於開始時間則加「結束日期待確認」；管理員可進入原編輯器確認，一般成員看相同狀態。不得直接顯示翌日或產生延續提示。

兩端活動表單的時間區統一依序為「開始時間 → 結束時間 → 結束於 → 起訖摘要」，位置在活動基本資訊附近；桌面可並排，窄版依序垂直。`結束於` 提供「當日／翌日／其他日期」，舊資料另保留「未確認」。旅行無日期時「其他日期」改選「第幾天」。新建預設當日；結束時間早於開始時提出可操作的翌日建議，由使用者採用，不自動改動。允許明確選擇相同日而較早的當地時刻，不憑兩個時鐘值判錯。

跨國際換日線可能當地日期更早；資料模型預留有號日差，「其他日期」能表達較早的日期，摘要顯示真實日期。這類活動不套「接續前一天」提示。起訖均為使用者填寫的當地日期／時間，沒有時區資料時不推算 UTC、先後時長或「正在進行」。

## 延續提示規則

- 只從已明確設定正向跨日的活動投影；開始日仍以原時間排序。中間日顯示「接續 Day N · 活動名稱」，結束日補結束時間與「抵達／結束」，跨多日不錯標成「前一天」。
- 提示不計入當日活動數、不加入全選／15 項上限，也沒有編輯／刪除／附件的第二套入口；多選模式隱藏提示。只有提示的日仍可顯示「尚無當日活動」及新增入口。
- 同日有多個提示時，已知結束時間在前並依時刻排序，其他依來源 Day／活動原順序穩定排列；不和本日活動混算。
- 點「查看原活動」切到來源日並定位／強調原列，鍵盤與閱讀器焦點跟隨；App 可開原活動詳情並保留返回位置。跳轉仍經過現有未保存／未提交選取守衛。
- 只對已建立的日期卡片產生提示；不補空日、不延長旅行日期。超出旅行範圍仍在原活動顯示完整結束日期並提醒。
- 修改時間／結束日、刪除活動／來源日、修改旅行起日後，來源及所有相關日重新計算。目的日刪除不刪原活動；來源已失效時移除提示並提供可理解的返回結果。
- 不另存提示副本，不改支出、票券及照片歸屬，不自動擴大照片關聯的時間範圍；公開讀取只由既有可公開欄位投影，不能帶出訂位碼或私有附件。

## 資料、相容與影響盤點

目前 `ItineraryDay.activities` 與 contracts 只有 `time`／`endTime`，日日期由旅行開始日＋dayNumber 推導；不能只改文字而假定已有跨日語意。

建議新增可空的 `endDayOffset`（相對來源日的整數日差）：0＝當日、1＝翌日、負值＝較早的當地日期、null／舊資料缺欄＝未確認。以 date-only 運算推導日期，不受裝置時區／夏令時間影響。合理可選範圍與既有旅行／Day 上限的對應，需在 CD0 審查時定稿並讓兩端共用；不能讓客戶端接受無界整數。

| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| 共用寫入／恢復   | `itineraryMaintenance`／`itineraryWrite`、Web Actions、v2 commands；變更日差提高 revision，衝突摘要／刪除預覽包含新日期語意；凍結 payload、UUID hash、持久操作與歷史 receipt 均需相容 |

## 驗收重點

- **日期**：22:25→翌日00:20、當日較早時刻、跨月／跨年／閏日、跨多日、負日差、等時刻、起／迄任一未填、旅行無日期、跳日、旅行範圍外、舊資料未知；改旅行開始日期後兩端一致。
- **一致性**：同一活動 Web 建立→App 閱讀／修改→Web 讀回；舊 App 改標題不清除日差；AI 未提供日期不臆測；CSV／PDF／公開輸出與畫面日期一致。
- **版面**：相同 fixture 的 Web 320／375px、桌面、iPhone／iPad；四語、深淺色、200%／Dynamic Type、長名稱／日期／備註；資訊順序、按鈕位置／強弱、圖示／時間欄一致，無橫向溢出或裁字。
- **操作**：鍵盤與 VoiceOver、44px／pt 點擊範圍、選日／提示跳轉焦點、詳情返回、空日／唯讀／離線／pending、多選確認及整天刪除；日期變更使舊確認失效。
- **恢復**：重複提交、丟回應、重啟、拒絕後恢復、帳號切換與撤權；原 UUID／原 payload 重試不被新欄位預設改寫，不出現兩筆活動或殘留提示。

按根與 App 規範執行受影響行為測試、contracts 生成／檢查與跨 workspace 必要檢查；本文件只有規劃，不宣稱上述驗收已通過。完成後在這份文件濃縮成果／驗證／限制，再歸檔，不另建逐輪報告。
