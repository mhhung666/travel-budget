# 相簿上傳改善實作紀錄

日期：2026-10-01。對應 [研究文件](PHOTO_UPLOAD_RESEARCH.md) 的 A–C 階段；歷史資料盤點 D 不在本次範圍。

## 使用者看得到的改變

- 一次選取多張後，每張顯示等待、查重、壓縮、上傳、存入相簿及結果。最多同時處理三張，每張確認入庫後立即出現在相簿，不再等待 20 張完成。
- 保留新增、重複略過、失敗、停止的數量與逐張列表。可查看新增／既有照片，以及只重試失敗或停止的項目。
- 相同原檔改名後再次選取，同旅程可辨識；同批相同內容也先等待首份結果，避免重複壓縮／傳輸。同一張照片放到不同旅程仍可新增。
- 停止會中止進行中的 PUT 並停止排程；仍會向伺服器確認可能已完成的操作，保留已存照片。離開頁面停止尚未完成的工作，不承諾背景上傳或重新開頁後自動續傳。
- 空相簿與有照片的畫面共用一個持續掛載的上傳器；刷新相簿不會重設工作列表。顯示的是階段與張數，沒有傳輸 bytes 百分比。

## 儲存與重試契約

主要實作在 [photoUpload.ts](../../src/lib/photoUpload.ts)、[photoUpload.actions.ts](../../src/actions/photoUpload.actions.ts)、[photoUploadJobs.ts](../../src/lib/photoUploadJobs.ts)。

1. 原始 File 先計算 SHA-256，向伺服器查同旅程已存照片。hash 是成員提交的查重提示，不能作為讀檔授權或已上傳 bytes 的驗證。伺服器仍驗旅程成員、工作歸屬、物件大小及型別。
2. 壓縮後，以 client 產生的固定 `uploadId` 登記 `photouploadjobs`，DB 成功後才簽 URL。兩個物件的 key、預期大小、照片 metadata 與工作歸屬固定，重試不另配 key。
3. 重試先確認工作結果；已存直接回傳相同照片。未存則 HEAD 檢查兩個物件，只簽尚未完整存在的部分。暫時性 HEAD 失敗回錯誤，不當作不存在而覆寫。
4. `finishPhotoUpload` 再驗兩個物件，於同旅程交易保護下建立照片、更新工作結果。再次確認 hash 與容量；同時傳相同原檔時只留一張，另一份工作回傳 `duplicate` 並登記多餘物件待清。
5. 確認成功的 DTO 合併進相簿快取；整個選取工作結束後刷新一次。公開副本在回應後僅補產相關照片，公開讀取仍保留既有補產能力，不回退到含 GPS 的私有檔。

新照片保存 `sourceHash`、`sourceHashVersion = sha256-file-v1`、`sourceSize`；旅程與 hash 的條件式唯一索引只涵蓋有字串 hash 的資料。舊照片不回填虛構的原檔 hash。

## 清理範圍

- 新工作於登記／重新簽名時保留 24 小時期限；過期後不可重啟，必須新建工作。
- 每次現有清理 cron 最多掃描 100 筆到期工作，另受時間預算限制。與 finalize 共用 Trip 寫入保護，在交易內重新確認期限與引用，才建立既有 `blobcleanupjobs`。
- 真正刪除沿用既有持久重試與第二次清掃。重複工作的刪除時間延後至其工作期限之後，避免仍有效的簽名又寫回物件。
- 沒有對未完成工作設定 MongoDB TTL；追蹤紀錄不能在清理前消失。完成／過期工作目前保留，不另設自動刪除保留期。
- 舊前端使用的 `createPhotoUploadUrls` 也先登記工作。舊版入庫未更新工作狀態時，清理仍會檢查照片引用，保留已使用的物件。
- 刪除旅程同交易移除工作，後續由既有整旅程前綴清掃處理晚到的 PUT。上傳者退出旅程不會阻止系統清理。
- 每日 cron 表示回收不是即時；正式排程、R2/CORS 與 backlog 必須在部署環境確認。此改動不會自動盤點導入前已經殘留的物件。

## 上線順序

1. 先在目標資料庫執行 [索引遷移](../../migrations/20261001090000-photo-upload-jobs.js)：照片旅程＋hash 唯一索引、工作到期與旅程索引。遷移可重跑；不會刪除照片或上傳工作。回滾保留索引與工作，避免破壞尚未重新整理的客戶端。
2. 部署應用程式，確認既有 `/api/cron/trip-cleanup` 排程及 `CRON_SECRET` 有效。回應多出 `uploads_retired`，代表該次已交付物件清理的工作數，不是已刪除的物件數。
3. 在測試旅程驗收真實 R2 PUT、CORS、iPhone／Android 大檔、多張進度與公開分享副本；本機 mock 儲存測試不代表這些外部設定已驗證。

本次沒有執行正式資料庫遷移、正式 R2 列舉／刪除或部署。研究文件先獨立提交；功能提交依專案規則同步提升 minor 版本，版本以 package.json 為準。

## 驗證

本機檢查結果：一般測試 1,766 個通過、241 個依既有條件跳過；另行啟用的 MongoDB 上傳交易整合測試 12 個全數通過。Lint、格式檢查、TypeScript 與正式建置均通過。未執行真實 R2 上傳、手機實機或部署環境驗收。

- 前端佇列測試：25 張逐張完成、單檔錯誤隔離、相同 bytes 改名查重、PUT／finalize 回應遺失、同工作只補傳縮圖、容量不足停止排程、停止後保存已完成結果、大檔防線。
- action／storage 測試：先登記才簽名、權限與輸入驗證、缺少／錯誤物件不入庫、HEAD 404 與服務失敗分流、已完成工作直接回傳、單張公開副本延後處理。
- 元件測試：相簿張數從零增加仍保留上傳狀態、只重試失敗項目、停止與卸載中止請求。
- 本機獨立 MongoDB replica set：12 個交易整合情境，包含相同操作重送、兩人同時傳同 hash、條件式唯一索引、跨旅程隔離、工作歸屬、成員退出後清理、期限展延／到期、清理與 finalize 競態、刪檔失敗／二次清掃、舊客戶端引用保護、容量競態及旅程刪除。
- 新增 CI 的獨立 replica set 工作；一般測試未提供 `PHOTO_UPLOAD_TEST_MONGODB_URI` 時跳過資料庫整合套件。整合套件只接受 loopback 連線，使用隨機新資料庫，結束後只刪除該測試資料庫。

本機可用專用 replica set 重跑：

```sh
PHOTO_UPLOAD_TEST_MONGODB_URI='mongodb://127.0.0.1:27017/?directConnection=true&replicaSet=rs0' \
  pnpm exec vitest run src/__tests__/photoUploadJobs.integration.test.ts
```

歷史照片查重、舊孤兒盤點、關頁後自動恢復本機 File、感知相似照片辨識與精確上傳百分比均未實作。重新開頁後重選，已入庫的新照片會由原檔 hash 略過；前一次未入庫的工作由期限清理回收。
