## 1. 金額尾數顯示要一致

**修正前實測**：輸入 NT$123、兩人均分。

| 畫面項目 | 顯示金額 |
| --- | ---: |
| 第一人 | NT$62 |
| 第二人 | NT$62 |
| 已分配總額 | NT$123 |

使用者加總會得到 124，容易以為分帳算錯。回饋者只確認到顯示問題，沒有驗證儲存和結算。

**修正前程式狀況**（2026-09-17 核對）

- 分攤以分為單位計算並儲存：`allocateMoney` 用最大餘數法拆分，加總一定等於總額
  （[money.ts](../../../src/lib/money.ts)、[expenseSplit.ts](../../../src/lib/expenseSplit.ts)）。這個例子實際存的是每人 61.50。
- `formatCurrency` 本身會顯示最多兩位小數，但 JPY 目前強制顯示整數
  （[currencies.ts](../../../src/constants/currencies.ts)）。
- 問題出在顯示前先 `Math.round`：[SplitSection.tsx](../../../src/components/trips/detail/expense-form/SplitSection.tsx)
  （每人分攤、已分配總額）、[ExpenseFormSheet.tsx](../../../src/components/trips/detail/expense-form/ExpenseFormSheet.tsx)、
  [TripExpenses.tsx](../../../src/components/trips/detail/TripExpenses.tsx) 共 7 處 `formatCurrency(Math.round(...))`。

**產品規則（已實作）**

> 所有帳內金額保留至小數點後兩位，顯示時省略末尾的零。分攤明細使用實際分配金額，
> 不得自行取整；同一幣別下，完成分配的個別金額加總須等於總額。
> 尾差沿用最大餘數法分配，餘數相同時依固定成員順序決定，所有畫面保持一致。

| 情境 | 顯示規則／範例 |
| --- | --- |
| 整數金額 | `NT$123`，不補 `.00` |
| 有小數 | `NT$61.5`、`NT$33.34`，省略末尾的零，最多兩位小數 |
| 123 元兩人均分 | `NT$61.5 + NT$61.5 = NT$123` |
| 100 元三人均分 | `NT$33.34 + NT$33.33 + NT$33.33 = NT$100` |
| 表單摘要、個別分攤、支出詳情、結算 | 同一筆金額使用相同精度，不另外四捨五入成整元 |

- **尾差歸屬**：以 `0.01` 為單位，優先分給計算餘數較大的人；餘數相同時依固定成員順序分配。
  重新開啟或切換畫面不得改變既有分攤的尾差歸屬，也不得因畫面排序而重新分配。
- **均分摘要**：只有每人實際分攤完全相同時才能顯示「每人 X 元」。若有尾差，例如 100／3，
  顯示「3 人均分」，個別明細列出實際分攤金額。
- **日圓與外幣**：JPY 的帳內分攤若有小數也必須保留，不得因幣別而隱藏實際分攤精度。
  外幣換算的參考金額標示「約」，與帳內精確金額區分；參考金額不作為分攤加總驗收依據。
- **整元還款**：本項沿用現有分精度的儲存與結算方式。若未來要支援整元還款，另訂尾差由誰承擔、
  如何記錄及判定結清的規則，不在本次顯示修正中處理。

**完成條件**

- 表單摘要、個別分攤、支出詳情、結算用同一套規則，不能各自四捨五入。
- 同一幣別下，完成分配的個別金額加總，一定等於顯示的總額。
- 整數不補 `.00`，小數省略末尾的零；JPY 帳內分攤也不可隱藏小數。
- 均分有尾差時，摘要不以單一金額宣稱「每人 X 元」；換算參考金額標示「約」。
- 補測試：123／2 顯示 61.5／61.5，100／3 顯示 33.34／33.33／33.33，並涵蓋 JPY 小數分攤。
  驗證表單預覽、儲存後詳情與結算的金額一致，各處分攤加總等於總額，重新開啟及切換畫面不改變尾差歸屬。

**實作結果**（2026-09-17）

- `formatCurrency` 不再對 JPY 取整，所有幣別最多兩位小數、省略末尾的零。
- 移除表單分攤列、已分配摘要、換算摘要與支出分組小計的 `Math.round`；分組小計改用 `roundMoney` 收斂浮點誤差。
- 均分摘要只在每人分攤完全相同時顯示「每人 X」，有尾差時改用 `form.summary.equalSplitUneven`（「3 人均分」）。
- 結算方案切換外幣時，換算金額以 `settlement.approxAmount` 標「約」，括號內的 TWD 維持帳內精確金額。
- 儲存、結算計算不變，不需要資料遷移。
- 測試：[splitAmountDisplay.test.tsx](../../../src/__tests__/splitAmountDisplay.test.tsx) 涵蓋 123／2、100／3、JPY 小數分攤、
  表單預覽、重新開啟既有分攤不改尾差歸屬，以及結算外幣「約」標示。

**驗收結果**（2026-09-17）

- 程式碼審查與 82 個相關自動化測試通過，未發現阻擋問題；涵蓋金額格式、分攤、表單顯示、結算與金額一致性。
- TypeScript 型別檢查、修改檔案的 ESLint 與 `git diff --check` 通過。
- 本次未進行瀏覽器實際操作；儲存後詳情以程式碼核對，尚未涵蓋完整的跨畫面端對端驗證。
- 非阻擋待改善：編輯表單測試仍有 React `act(...)` 警告，後續應等待非同步更新完成以清除警告。

## 2. 結算空白頁不再像已完成

**修正前實測**：主標題已改成「尚無需要結算的支出」（第二輪第 6 項），但下面仍有：

- 每位成員「已結清」
- `+NT$0`
- 「已結清紀錄」
- 「登記還款」

整體還是像一張完成結算的報表。

**建議**

- 沒有任何支出時，主要呈現「尚無支出＋記第一筆」。
- 成員餘額標示改為「尚無分攤」，不用「已結清」，也不顯示 `+NT$0`。
- 「已結清紀錄」沒有資料時隱藏或改成空白提示。
- 「登記還款」若要支援預付款，應明確說明用途；否則沒有支出時降低顯示層級。

**相關程式**

- [SettlementBalances.tsx](../../../src/components/settlement/SettlementBalances.tsx)（依旅行是否有支出或還款，區分「尚無分攤」與零餘額的「已結清」）
- [SettlementSummary.tsx](../../../src/components/settlement/SettlementSummary.tsx)、[SettlementPlan.tsx](../../../src/components/settlement/SettlementPlan.tsx)（第二輪已處理的空白分岔，沿用同一判斷）

**注意**：有支出但個人餘額剛好為 0，仍應顯示「已結清」或「無需轉帳」，只有「沒有支出」才改文案。

**實作結果**（2026-09-17）

- 每人統計：旅行沒有支出也沒有還款時，成員改標 `settlement.noShareYet`（「尚無分攤」），不顯示 `+NT$0` 與「已付／分攤 NT$0」。
  只要有支出或還款，餘額為 0 仍標「已結清」。
- 已結清紀錄：沒有支出時，「登記還款」降為次要按鈕；成員看到的空白提示改為 `settlement.paymentHistoryNoExpenses`，
  說明出發前的訂金或代墊款也可以先登記。唯讀檢視維持原本的「尚無還款紀錄」。
- 摘要與結算方案沿用第二輪的空白分岔，未改動。
- 測試：[settlementEmptyStates.test.tsx](../../../src/__tests__/settlementEmptyStates.test.tsx) 補上每人統計與還款紀錄的空白／有支出情境。

**驗收結果**（2026-09-17）

- 程式碼審查與 55 個相關自動化測試通過，未發現阻擋問題；涵蓋空白旅行、記第一筆支出按鈕、有支出的零餘額、還款結清、預付款提示與唯讀權限。
- TypeScript 型別檢查、修改檔案的 ESLint 與 `git diff --check` 通過。
- 本次為程式碼與自動化測試驗收，未進行瀏覽器實際操作。

## 3. 說清楚「切換旅行」會怎麼處理草稿

**現況**：表單有內容時按「切換旅行」，原旅行的草稿會保留，另一趟開啟自己的表單。實測確認隔離行為正確。

**問題**：使用者可能是填完才發現選錯旅行，會以為內容會一起帶過去。

**建議**：表單有內容時，在切換旅行附近補一句說明，例如：

> 草稿會保留在澎湖，切換後開啟另一趟旅行的記帳表單。

「將這筆移到另一趟」是新功能，這一輪不做。未來若要支援，應提供明確操作，並要求重新確認付款人與分帳對象。

**相關程式**：[ExpenseFormSheet.tsx](../../../src/components/trips/detail/expense-form/ExpenseFormSheet.tsx)（`form.switchTrip`）

**實作結果**（2026-09-17）

- 新增模式的表單有內容時，「切換旅行」左側顯示 `form.switchTripDraftHint`（「草稿會保留在「{trip}」，切換後開啟另一趟旅行的記帳表單。」），
  並以 `aria-describedby` 關聯到按鈕。表單沒填內容時不顯示。
- 編輯模式不顯示：編輯不留草稿，切換前會先問是否捨棄修改。切換行為本身未改動。
- 測試：[expenseFormLayout.test.tsx](../../../src/__tests__/expenseFormLayout.test.tsx) 驗證空白表單不顯示、輸入金額後顯示並關聯按鈕。

**驗收結果**（2026-09-17）

- 程式碼審查與 13 個相關自動化測試通過，未發現阻擋問題；涵蓋提示顯示與按鈕關聯、切換前立即保存草稿、各旅行草稿隔離、重新開啟恢復內容，以及編輯與儲存失敗時的離開確認。
- TypeScript 型別檢查、修改檔案的 ESLint 與 `git diff --check` 通過。
- 本次未進行瀏覽器實際操作；草稿恢復測試仍有非阻擋的 React `act(...)` 警告。

## 4. 地圖統計標籤要說清楚範圍

**修正前實測**：同一列顯示「2 趟旅行」（含未出發、未排日期）、「0 個國家、0 個城市」（排除計畫中），以及「另有 1 個計畫中國家」。
數字沒錯，但各指標範圍不同，要使用者自己推敲。

**最小修改**：只改標籤。

| 現有標籤 | 建議 |
| --- | --- |
| 旅行 | 已建立旅行 |
| 國家 | 已造訪國家 |
| 城市 | 已造訪城市 |

整列統一切換「已出發／計畫中」是更大的改動，這一輪先不做。

**相關程式**：[MapStatsBar.tsx](../../../src/components/map/MapStatsBar.tsx)（`statTrips`、`statCountries`、`statCities`）

**注意**：公開地圖分享也用同一個統計列，但它不區分計畫中（見第二輪第 7 項）。改標籤時要確認公開頁的文字仍正確，
必要時公開頁用另一組標籤。

**實作結果**（2026-09-17）

- 私人地圖的統計列改用 `map.statTripsCreated`／`statCountriesVisited`／`statCitiesVisited`（「已建立旅行」「已造訪國家」「已造訪城市」），
  由 `MapStatsBar` 的 `distinguishPlanned` 開啟。「另有 N 個計畫中」註記與統計數字不變。
- 公開地圖分享不傳 `planned`，國家／城市含未出發旅行，標上「已造訪」會不正確，因此維持原本的「旅行／國家／城市」。
- 測試：[mapStatsLabels.test.tsx](../../../src/__tests__/mapStatsLabels.test.tsx) 驗證私人與公開兩組標籤。

**驗收結果**（2026-09-17）

- 程式碼審查與 9 個相關自動化測試通過，未發現阻擋問題；涵蓋私人與公開地圖標籤、已出發與計畫中地點的統計範圍、計畫中國家註記，以及飛行里程資料來源。
- 確認四種語系均補齊新標籤，私人地圖啟用新標籤，公開地圖保留通用標籤。
- TypeScript 型別檢查、修改檔案的 ESLint 與 `git diff --check` 通過。
- 本次未進行瀏覽器實際操作，窄螢幕與各語系的標籤截斷情況尚未實測。
